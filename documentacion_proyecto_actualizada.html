1. Descripción General del Proyecto

¿Cuál es el objetivo principal del proyecto?
HealthPredict Enterprise es una plataforma integral de monitoreo y prevención de salud diseñada específicamente para entornos empresariales. El sistema se enfoca en:

Monitoreo Preventivo:
  • Seguimiento continuo de métricas de salud de trabajadores de oficina
  • Análisis de patrones de estrés y bienestar
  • Integración con dispositivos smartband para recolección de datos biométricos

Administración Empresarial:
  • Panel de control para administradores con múltiples usuarios
  • Reportes y estadísticas de salud organizacional
  • Mensajería preventiva contextualizada

Reportes Personalizados:
  • Generación de informes individuales para exámenes médicos preventivos
  • Exportación de métricas de salud personalizadas
  • Historial de salud individual y tendencias

Evidencias de Pertinencia Laboral

  • Estudios de mercado sobre necesidades de salud empresarial
  • Entrevistas con profesionales de RRHH
  • Análisis de casos de éxito en empresas similares
  • Documentación de requerimientos del cliente

8. Arquitectura Técnica Detallada

¿Cuál es la arquitectura completa del sistema HealthPredict?
1. Arquitectura de Capas (N-Tier):
  • Capa de Presentación: Angular 15+ (Frontend Web), Android (App Móvil), iOS (App Móvil)
  • Capa de Servicios: ASP.NET Core 7.0 Web API con patrón Repository
  • Capa de Lógica de Negocio: Business Logic Layer (BLL) con servicios especializados
  • Capa de Acceso a Datos: Entity Framework Core 7.0 con PostgreSQL
  • Capa de Integración: APIs externas, Health Connect, HealthKit

2. Patrón de Diseño Implementado:
  • Repository Pattern: Para abstracción de acceso a datos
  • Dependency Injection: Para inversión de control y testabilidad
  • MVVM (Model-View-ViewModel): En aplicaciones móviles
  • Service-Oriented Architecture: Para modularidad y escalabilidad

3. Microservicios y Componentes:
  • API Gateway: Punto único de entrada para todas las solicitudes
  • Servicio de Autenticación: JWT tokens y autorización basada en roles
  • Servicio de Datos Vitales: Procesamiento de métricas de salud
  • Servicio de Alertas: Sistema de notificaciones inteligentes
  • Servicio de Reportes: Generación de informes PDF con wkhtmltopdf

10. Base de Datos y Modelo de Datos

¿Cómo está estructurada la base de datos y qué entidades maneja?
1. Entidades Principales:
  • Usuario: ID, Nombre, Apellido, Email, FechaNacimiento, Género, Altura, Peso, etc.
  • DatoVital: ID, UsuarioID, TipoDato, Valor, Unidad, FechaRegistro, DispositivoOrigen
  • Alerta: ID, UsuarioID, TipoAlerta, Descripción, Severidad, FechaCreación, Leída, Resuelta
  • Dispositivo: ID, UsuarioID, Nombre, Tipo, Token, FechaVinculación
  • Reporte: ID, UsuarioID, TipoReporte, FechaGeneración, RutaArchivo

2. Relaciones y Constraints:
  • Usuario → DatosVitales: Relación 1:N con cascade delete
  • Usuario → Alertas: Relación 1:N con índices optimizados
  • Usuario → Dispositivos: Relación 1:N con unique constraints
  • Índices Compuestos: (UsuarioID, FechaRegistro) para consultas temporales
  • Particionamiento: Por fecha para optimizar consultas históricas

3. Configuración PostgreSQL:
  • Provider: Neon Database (Serverless PostgreSQL)
  • Connection String: SSL requerido con Trust Server Certificate
  • Migrations: Entity Framework Code-First approach
  • Backup Strategy: Snapshots automáticos diarios
  • Performance: Connection pooling y prepared statements

11. APIs y Endpoints Detallados

¿Qué endpoints específicos expone la API y cómo funcionan?
1. Controlador de Datos Vitales (/api/DatosVitales):
  • GET /usuario/{id}: Obtiene todos los datos vitales de un usuario
  • GET /{id}: Obtiene un dato vital específico por ID
  • POST /: Crea un nuevo registro de dato vital
  • PUT /{id}: Actualiza un dato vital existente
  • DELETE /{id}: Elimina un dato vital
  • POST /Sync/HealthKit: Sincronización masiva desde dispositivos móviles
  • GET /estadisticas: Estadísticas agregadas por tipo y período

2. Controlador de Alertas (/api/Alertas):
  • GET /usuario/{id}: Alertas de un usuario específico
  • GET /usuario/{id}/noleidas: Alertas no leídas
  • GET /usuario/{id}/severidad/{nivel}: Filtro por severidad
  • POST /{id}/marcarleida: Marcar alerta como leída
  • POST /{id}/resolver: Resolver alerta con notas
  • POST /: Crear nueva alerta

3. Controlador de Gráficos (/api/Graficos):
  • GET /DatosVitales/{usuarioId}/{tipoDato}: Datos para gráficos específicos
  • GET /TiposDeDatos/{usuarioId}: Tipos de datos disponibles
  • GET /ResumenDatosVitales/{usuarioId}: Resumen estadístico
  • GET /ComparativaMensual/{usuarioId}/{tipoDato}: Análisis temporal

4. Controlador de Reportes (/api/Reportes):
  • GET /DatosVitales/{usuarioId}: Genera PDF con datos vitales
  • GET /DatosVitales/{usuarioId}?tipoDato={tipo}: Reporte filtrado
  • Response Type: application/pdf con headers de descarga

12. Seguridad y Autenticación

¿Cómo se implementa la seguridad en el sistema?
1. Autenticación JWT:
  • Token Generation: HS256 algorithm con secret key
  • Claims: UserID, Role, Email, Expiration
  • Refresh Tokens: Para renovación automática de sesiones
  • Token Validation: Middleware personalizado en cada request

2. Autorización Basada en Roles:
  • Roles: Admin, Doctor, Usuario, SuperAdmin
  • Policies: Definidas en Startup.cs con requirements
  • Resource-Based Authorization: Los usuarios solo acceden a sus datos
  • Action Filters: Validación automática de permisos

3. Protección de Datos:
  • HTTPS Only: SSL/TLS obligatorio en producción
  • Data Encryption: Campos sensibles encriptados en BD
  • Input Validation: Data Annotations y FluentValidation
  • SQL Injection Prevention: Entity Framework con parámetros
  • CORS Policy: Configurado para dominios específicos

4. Auditoría y Logging:
  • Request Logging: Todas las peticiones HTTP registradas
  • Error Tracking: Serilog con structured logging
  • User Activity: Registro de acciones críticas
  • Performance Monitoring: Métricas de respuesta y throughput

13. Integración con Dispositivos de Salud

¿Cómo se integra el sistema con dispositivos wearables y de salud?
1. Android - Health Connect Integration:
  • API: androidx.health.connect.client
  • Permisos: READ_HEART_RATE, READ_STEPS, READ_WEIGHT, etc.
  • Data Types: HeartRateRecord, StepsRecord, WeightRecord
  • Sync Strategy: Incremental sync desde última fecha
  • Supported Devices: Fitbit, Samsung Health, Google Fit

2. iOS - HealthKit Integration:
  • Framework: HealthKit.framework
  • Authorization: HKHealthStore.requestAuthorization
  • Data Types: HKQuantityType (heart rate, steps, weight)
  • Queries: HKAnchoredObjectQuery para datos incrementales
  • Background Sync: HKObserverQuery para actualizaciones automáticas

3. Mapeo de Datos:
  • Heart Rate: Android HEART_RATE → iOS HKQuantityTypeIdentifierHeartRate
  • Steps: Android STEPS → iOS HKQuantityTypeIdentifierStepCount
  • Weight: Android WEIGHT → iOS HKQuantityTypeIdentifierBodyMass
  • Blood Pressure: Sistólica/Diastólica con unidades mmHg
  • Sleep: Duración en horas con análisis de calidad

4. Procesamiento de Datos:
  • Validation: Rangos médicos válidos (FC: 30-220 bpm)
  • Deduplication: Evitar datos duplicados por timestamp
  • Aggregation: Promedios diarios, máximos, mínimos
  • Alert Generation: Algoritmos para detectar anomalías

16. Performance y Optimización

¿Qué optimizaciones se implementaron para el rendimiento?
1. Backend Optimizations:
  • Entity Framework: Lazy loading, Include() para eager loading
  • Database Indexing: Índices compuestos en (UsuarioID, FechaRegistro)
  • Query Optimization: Proyecciones específicas con Select()
  • Caching: MemoryCache para datos frecuentemente accedidos
  • Pagination: Skip/Take para grandes conjuntos de datos

2. Frontend Optimizations:
  • Angular: OnPush change detection, lazy loading modules
  • HTTP Interceptors: Caching de responses, retry logic
  • Observables: Debounce, distinctUntilChanged para búsquedas
  • Virtual Scrolling: Para listas grandes de datos
  • Tree Shaking: Eliminación de código no utilizado

3. Mobile Optimizations:
  • Android: ViewBinding, Kotlin Coroutines para async
  • Network: Retrofit con connection pooling
  • Local Storage: Room database para cache offline
  • Background Sync: WorkManager para sincronización programada

4. Database Performance:
  • Connection Pooling: Configurado en PostgreSQL
  • Prepared Statements: Para prevenir SQL injection y mejorar performance
  • Partitioning: Tablas particionadas por fecha
  • Monitoring: Query performance tracking
